## 一、管线架构优化

### 🔴 高优先级

| # | 问题 | 现状 | 建议 | 改动量 |
|---|------|------|------|--------|
| **1** | **评分纯串行 — 速度瓶颈** | `agentScorer()` 逐题串行：102题 × 2次API调用 × 200ms间隔 ≈ 40分钟/轮 | 用 Promise 池并发 3-5 个评分请求，降到 ~10分钟/轮。评分之间无依赖 | ~10 行 |
| **2** | **无断点续跑** | 进程崩溃 = 当前轮次全部评分结果丢失（FAQ 保存了但分数没保存） | Scorer 每 10 题 checkpoint 到临时文件；启动时 `--resume` 恢复 | ~40 行 |
| **3** | **无收敛检测 — 盲跑固定轮数** | `for (let cycle = 1; cycle <= CFG.cycles; cycle++)`，不管分数是否已 plateau 都跑满 30 轮 | 连续 3 轮均分波动 < 1 分且无新 FAQ 生成 → 自动终止 | ~20 行 |
| **4** | **FAQ 去重仅精确匹配** | `applyFixes()` 只检查 `e.q === newEntry.q`，语义高度近似的条目照加不误 | 用关键词 Jaccard 系数或标题 embedding 余弦相似度（>0.85 则合并） | ~30 行 |

### 🟡 中优先级

| # | 问题 | 建议 | 改动量 |
|---|------|------|--------|
| **5** | **BM25 索引每次查询都重建** — `kbIndex()` / `corpusIndex()` 虽已缓存，但 FAQ 匹配 `matchFAQ()` (563条 × 平均10个key × 逐条 `includes`)是 O(N×K) 暴力扫描 | 为 FAQ 预建倒排索引 (keyword → FAQ IDs)，查询 O(1) | ~20 行 |
| **6** | **语料校准(戊)仅阶段0跑一次** — 后续 FAQ 新增/修改后未经语料库校准 | 每 5 轮或 FAQ 净增 >20 条时触发增量校准 | ~15 行 |
| **7** | **出题分配固定而非自适应** — Generator 每分类等量出题，不参考上轮弱项 | 弱分类（均分最低 3 个）出题量 ×1.5~2，强分类减量 | ~20 行 |
| **8** | **Validator 修正未反馈给 Generator** — 丁校验出无效题目后仅记录，Generator 不知道哪里出了错 | 将 Validator 典型 issue 汇总注入 Trainer prompt，形成质量闭环 | ~15 行 |
| **9** | **FAQ 的 `subfield` 分类不一致** — 多条 FAQ（如"实验教学目标""实验涉及哪几类反应"）被错误标记为 `光化学应用`，管道和前端都继承了这个错误 | 跑一轮分类校验脚本修正（详见内容部分 #2） | 脚本 + 批量修正 |

### 🟢 低优先级

| # | 问题 | 建议 | 改动量 |
|---|------|------|--------|
| **10** | 甲(Trainer)和乙(Generator)在非首轮可并行（甲只依赖上轮分数，乙只依赖 FAQ） | 用 `Promise.all` 并行启动 | ~10 行 |
| **11** | 评分 4 维 × 25 分缺乏锚定样例（rubric），导致 LLM 评分标准跨轮次漂移 | 为每档（0/5/10/15/20/25）提供 1-2 个锚定样例 | prompt 修改 |
| **12** | 管线输出文件累积严重 — `test_questions_core_r1.json` 到 `r19.json` 共 19 轮 + 多个 `structured_output_*.json` 未清理 | 归档旧输出或自动清理 | 脚本 |

## 二、前端优化

### 🔴 高优先级

| # | 问题 | 现状 | 建议 | 改动量 |
|---|------|------|------|--------|
| **13** | **FAQ 直接嵌入 HTML → 571KB** | ~560 条 FAQ 完整内嵌为 `const FAQ=[...]`，导致：首屏需解析 1.5MB+、每次 FAQ 更新需 `--sync-html`、数据双写（JSON + HTML） | FAQ 改为 `fetch('data/faq_unified.json')` 动态加载。HTML 体积可缩小 ~60%，数据源单一化 | ~50 行 |
| **14** | **搜索 O(N×M) 全量扫描** | `searchCorpus()` 每次对 291 篇文献做逐字段 `includes`，且每次重新 `norm()` 所有字段 | `loadCorpus()` 时预计算 norm 字段；建倒排索引；或放 Web Worker 避免阻塞 UI | ~30 行 |
| **15** | **测评评分用关键词覆盖率 — 对学生不公平** | `coverageOf()` 把学生回答与硬编码 keyword groups 做 `includes` 匹配。写"Fe²⁺盐先沉淀再氧化"如果没命中"莫尔盐"这个 exact key，得 0 分 | 接入 LLM 做语义评分（已有 `callLLM` 函数但测评中没用），或至少用 embedding 相似度替代 | ~30 行 |

### 🟡 中优先级

| # | 问题 | 建议 | 改动量 |
|---|------|------|--------|
| **16** | **LLM 和本地回答二选一，不能互补** — LLM 启用时跳过本地文献卡片/MSDS/视频 | LLM 做主回答，但本地文献卡片、MSDS、视频作为补充始终附加 | ~20 行 |
| **17** | **fetch 路径用了反斜杠** — 第 408 行 `'data\corpus.json'`，在 Linux/Mac 会 404 | 改为 `'data/corpus.json'` | 1 字符 |
| **18** | **打字动画是假延迟，不是真流式** — `aiSay()` 按长度估算延迟后一次性显示 | 如 DeepSeek API 支持 `stream: true`，可实现逐字流式输出 | ~20 行 |
| **19** | **5 个 HTML 页面各自独立 — CSS 大量重复** — `corpus.html`、`main.html`、`knowledge.html`、`assistant.html`、`prep.html` 各自重定义相同的 CSS 变量和工具类 | 提取共用 CSS 文件，或考虑统一为 SPA | 较大 |

### 🟢 低优先级

| # | 问题 | 建议 | 改动量 |
|---|------|------|--------|

| **21** | 测评 8 知识点完全硬编码在 JS 中 — 修改需编辑 HTML | 提取到独立 JSON，动态加载 | ~20 行 |
| **22** | 对话历史仅 localStorage — 上限 60 条、无跨设备 | 提供对话导出功能 | ~15 行 |
| **23** | FAQ 数组末尾有重复注释片段 `/* FAQ 匹配/* FAQ 匹配` — sync 工具残留 | 修复 `syncFAQtoHTML()` 或废弃嵌入方案（见 #13） | 1 行 |

## 三、数据架构优化

| # | 问题 | 建议 |
|---|------|------|
| **24** | **KB（1335条）与 FAQ（709条）100% 重叠** — `kb.json` 所有条目标题与 FAQ 匹配，但 KB 条目没有 `subfield` 字段，只有 `chapter`（ch1/ch2），导致管线中 `bm25MatchKB()` 可以做关键词检索但无法按分类筛选 | 考虑废弃 `kb.json` 或将两者合并，统一使用带 `subfield` 的 FAQ 格式 |

## 四、内容质量问题

### 🔴🔴🔴 严重：烘干温度存在致命矛盾

FAQ 中同时存在两种互相矛盾的烘干温度，会直接误导学生操作、毁掉产物：

| 条目 | 给出的烘干温度 | 正确？ |
|------|---------------|--------|
| `烘干温度时间` | **50℃**，"严禁超过50℃" | ✅ |
| `烘箱温度为何50度` | **50℃**，"110℃为失水温度非烘干温度" | ✅ |
| `结晶操作参数` | **50℃** | ✅ |
| `第四步烘干条件` | **50℃** | ✅ |
| `热行为与分解温度` | **50℃以下** | ✅ |
| `温度控制总结` | **≤50℃** | ✅ |
| `产率过高原因` | **110℃** 烘干1-2小时 | ❌ **错误！** |
| `完整操作流程` | **110℃** 烘干1-2小时 | ❌ **错误！** |
| `产率优化策略` | **≤110℃** | ❌ **错误！** |
| `各阶段温度一览` | **110℃**×1-2小时 | ❌ **错误！** |
| `各阶段时间一览` | **110℃**×1-2小时 | ❌ **错误！** |
| `热分解三阶段` | "推荐**110℃**烘干1-2小时" | ❌ **错误！** |
| `烘干后产物变色诊断` | "标准为**110℃**" | ❌ **错误！** |
| `设备故障处理` | "≤110℃" | ❌ **错误！** |
| `加热步骤有哪些` | "烘干步骤（110°C）" | ❌ **错误！** |

**事实**：Manual ch4-s1 明确规定烘干温度为 **50℃**。产物约 113℃ 失结晶水，110℃ 仅差 3℃ 极度危险。7 条正确、8 条错误 — 错误条目均来自管线 LLM 生成。

> ⚠️ 这是最严重的内容问题。学生如果看错了条目，110℃ 烘干会让产物脱水变质、实验失败。

### 🟡 中等：319/709 条 FAQ（45%）没有 detail 字段

近一半条目缺少扩展解释。对于教学平台来说，"为什么"往往比"是什么"更重要，而 detail 正是承载"为什么"的地方。首批缺失 detail 的条目包括：

- `第一个配位化合物的发现`（化学史）
- `配位化学发展四阶段`（配位化学理论）
- `磁学性质`（磁性研究）
- `稳定常数数据`（分析测定）
- `配位反应自由能`（综合研究）

### 🟡 中等：评分维度缺乏化学专业性

管线 4 维度评分（准确性/完整性/来源引用/清晰度），各 25 分：

| 缺失维度 | 为什么重要 |
|----------|-----------|
| **安全性提示** | 涉及有毒/腐蚀性试剂的回答必须标注安全警告。如回答"加 H₂O₂"但未提"戴手套、通风"，应扣分 |
| **化学符号规范** | 写 `Fe` 而不是 `Fe³⁺`、缺单位、方程式未配平 — 这在化学教学评分中必须扣分 |
| **与问题的相关性** | AI 可能给出正确但答非所问的内容（如问"产率怎么算"却答"晶体结构"） |

建议调整后的评分维度：**准确性 30 / 完整性 20 / 化学规范性 15 / 来源引用 15 / 清晰度 10 / 安全性 10 = 100**
